## Verdict

**The app is built correctly.** The security boundary, the data model, the
test suite, and the migration discipline are all well above what a project
this size normally has. Nothing here calls for a rewrite or a structural
retreat.

Two defects are worth stopping for, and they are the two where the blast
radius is production data rather than a bad render:

1. **A cascade `SET NULL` collides with the pack-rank unique index**, so
   deleting a list, deleting an account, or deleting a container item can
   500. Reproduced end to end.
2. **Production migrations deploy with no machine gate on CI**, and on this
   repo's plan the gate the workflow's own comment assumes cannot exist.

Everything after those two is ordinary improvement work.

## Critical

### C1. Cascade `SET NULL` on `packing_location_id` collides with the pack-rank unique index

**Status: reproduced against the repo's real 19 migrations, with D1's FK
semantics (`PRAGMA foreign_keys = ON`).**

`server/db/app-schema.ts:255-258` declares `packing_location_id` with
`onDelete: 'set null'`. `app-schema.ts:311-315` declares a partial unique
index over the Unassigned cohort:

```sql
list_items_pack_unassigned_uq (list_id, pack_sort_order) WHERE packing_location_id IS NULL
```

When a `packing_locations` row disappears **via a cascade** rather than via
`packingLocations.remove()`, its contents are set to `packing_location_id =
NULL` while **keeping their old `pack_sort_order`**. They land in the
Unassigned cohort carrying a rank an existing Unassigned row already holds,
and the partial unique index rejects the whole statement.

`packingLocations.remove()` (`server/repos/packing-locations.ts:228-301`) is
the **only** delete path that re-ranks orphans to `max+1...` first. Its own
comment anticipates the collision and deliberately chooses rollback. Every
other path is a bare delete: `lists.remove()`
(`server/repos/lists.ts:214-221`) and `listItems.remove()`
(`server/repos/list-items.ts:436-448`) do nothing, and account deletion goes
through better-auth's `deleteUser`, which nobody in this repo wrote.

**The triggering state is the ordinary first-use shape of Pack mode**: some
items still Unassigned, one item dragged into a bag (which appends at rank 0
*of the bag's cohort*, while Unassigned still holds a rank-0 row).

Reproduced results:

| Path | Result |
| --- | --- |
| `DELETE /api/lists/:id` | **UNIQUE constraint failed** |
| Settings -> delete account | **UNIQUE constraint failed** |
| `DELETE /api/lists/:id/items/:itemId` where the item backs a container | **UNIQUE constraint failed** |
| `DELETE /api/gear-items/:id` where the gear backs a container | **UNIQUE constraint failed** |
| `DELETE /api/gear-items/:id` for gear merely *inside* a bag | OK - cascades the membership row away entirely, no `SET NULL` |

Account deletion failing is the worst of these: the user has no workaround,
and it is the one action the app promises is always available.

**Why the tests miss it.** `server/routes/packing-locations.test.ts:756`
("cascades locations on list delete") uses one item and moves it into the
location, leaving Unassigned empty. `:417` uses two items, but deleting the
container frees the colliding rank first. Every existing test sits in the
non-colliding corner.

**Fix.** This needs a design decision, not a patch, because the FK action
runs before any trigger could re-rank. Options, in the order I would
consider them:

- Drop the FK cascade to `NO ACTION` and make every deletion path re-rank
  explicitly. Clean, but the `user` cascade path is not ours to control.
- Make `pack_sort_order` nullable and treat NULL rank as "unranked, sorts
  last", so the cascade's leftover rank stops being a uniqueness claim.
- Drop the Unassigned partial index and enforce cohort uniqueness only at
  write time.

Whichever way it goes, the regression test needs **two** Unassigned rows -
that is the difference between the current tests and the bug.

### C2. Production D1 migrations deploy with no machine gate on CI

`.github/workflows/deploy.yml:20-22` triggers on `push: branches: [main]`
with no `workflow_run`, no `needs:`, no `environment:`, and no conditional.
It then runs `wrangler d1 migrations apply grampacker --remote` against
production. `ci.yml` runs independently on the same push. **They race.**

The workflow's own header comment states the assumed control:

> a PR is verified by ci.yml and (with branch protection + auto-merge) can
> only reach main once those checks pass

**That premise is false on this repository.** `grampacker` is private on a
free GitHub plan; both the branch-protection and rulesets APIs return:

```
403 Upgrade to GitHub Pro or make this repository public to enable this feature.
```

So there is no branch protection, and `--auto` has no protection to wait on.
CLAUDE.md's "branch protection will merge even while checks are still
running" understates it - the gate does not exist at all. The only thing
standing between a data-destroying migration and production is a human or
agent remembering to look at CI.

This matters specifically because `npm run test:migrations` is the check
AGENTS.md calls *"ENFORCED, not left to discipline"*, written after
migration 0009 cascade-deleted every `list_items` row in production. It is
currently not enforced; it is racing the thing it guards.

Secondary: migrations apply **before** `npm run deploy`, so a build failure
leaves production on new schema with old code and no rollback path. The
comment at `deploy.yml:59-62` scopes this to "additive-only migrations", but
0009 and 0016 were both table rebuilds.

**Fix (one of):**

- `on: workflow_run: {workflows: [CI], types: [completed]}` plus
  `if: github.event.workflow_run.conclusion == 'success'`. Works on the free
  plan, no upgrade needed. This is the one I would do.
- Or run the verify steps inline in `deploy.yml` before the migrate step, so
  the deploy job gates itself.
- A GitHub Environment with a required reviewer also works, but is a heavier
  process change.

## Important

### Server

- **`requireSession` runs 2-3x per request** on the whole `/api/lists`
  surface. `server/index.ts:81-85` mounts three sub-apps on the same base and
  each does `use('*', requireSession)`. Each invocation constructs a fresh
  better-auth instance and reads the `session` and `user` rows: 4 wasted D1
  reads per list request, 6 on food routes, on a Free-tier account whose
  per-invocation query budget AGENTS.md already flags as ambiguous. Fix:
  hoist to `api.use('/lists/*', requireSession)` and drop it from the three
  sub-apps.
- **`PATCH /api/lists/:id/items/:itemId` returns 500, not 409**, when a
  location move loses a race. `server/repos/list-items.ts:349-352` documents
  "the route answers 409", but `update()` has no try/catch and
  `listItemFailure` has no conflict branch. `reorderPack` gets this right;
  `update` was never brought in line. The comment is a false claim about
  behavior.
- **`chunkForParamCap`'s stated invariant is false.**
  `server/repos/chunk-ids.ts:29-40` counts JS object keys, but drizzle binds
  a parameter for **every insertable table column**, defaulting the ones the
  row omits. Nothing is broken today because all callers enumerate every
  column, but the margin is zero: `listFoodItems` is 9 keys -> 10 rows ->
  exactly 90 params. Add one defaulted column and forget it in the row
  literal, and the chunker still says 10 rows while drizzle binds 100. Derive
  the divisor from `getTableColumns(table).length`.
- **`POST /api/gear-items/import` can emit ~4000 statements in one batch**,
  and the DTO bound contradicts the DB bound: `shared/gear.ts:179-198` allows
  2000 items, but the `gear_items_user_cap` trigger aborts at 500 - so any
  import over 500 is guaranteed to 422 *after* D1 executed 500+ statements
  inside a transaction. Lower the schema max to `GEAR_ITEM_CAP` and reject
  early.
- **`categories` has no cap.** Every other user-owned table has a trigger;
  this one does not. Unbounded growth is reachable (import gear carrying new
  categories, bulk-delete the gear, repeat), and once past 500 the reorder
  endpoint physically cannot express an ordering (`shared/gear.ts:137` caps
  the payload at 500).
- **The migration-safety check does not compare CHECK constraints or foreign
  keys.** `scripts/check-migration-safety.mjs:975-980` reads only `trigger`
  and `index` rows from `sqlite_master`. A hand-written rebuild that silently
  dropped `list_items_gear_same_owner_fk` would pass every current assertion -
  and those composite same-owner FKs are what the whole authorization story
  leans on as its structural backstop. This is the cheapest high-value fix in
  the report.
- **Constraint races that should be 4xx surface as 500**: `food.ts:302-309`
  (concurrent day-trim -> FK violation, only `isSlotNotNeededError` caught),
  `list-items.ts:191-216`, `lists.ts:646-666`. `isForeignKeyViolation`
  already exists and is used elsewhere - apply it here.

### Client

- **A failed `['lists']` fetch renders "List not found" and wipes the
  persisted last-list pointer.** `src/lists/ListDetailPage.tsx:329` destructures
  only `isPending`; on error `data` is `undefined`, `lists` falls back to
  `[]`, and the page renders the terminal *"This list may have been deleted"*
  screen. Worse, the self-heal effect at `:442-450` is gated only on
  `listsLoading`, so it also calls `clearLastListPath()`. Two failed GETs
  (retry is `failureCount < 1`) and the user is told their list is gone and
  loses their `/` shortcut. `ListDetailStatus` already supports `onRetry`.
- **The same gap on `/lists` renders the brand-new-user empty state.**
  `src/lists/ListsPage.tsx:80` takes `isLoading` but not `isError` (which
  `useReorderable` does return, `use-reorderable.ts:202`), so a user with 40
  lists gets *"create your first list"* after a transient failure.
  `GearLibraryPage.tsx:572` handles exactly this correctly - these two are
  coverage gaps, not misunderstanding.
- **Every "reorder in flight" guard in Pack view is wired to the wrong
  mutation.** `reorderPackItemsMut.isPending` is read **nowhere** - the
  mutation appears only at its declaration and three `.mutate` calls
  (verified). All five consumers read `reorderItemsMut.isPending`, which in
  Pack mode never fires. The drag-disable, the click-to-place gate, and the
  move-menu gate are all permanently `false` in the mode they were written
  for.
- **The React Query cache survives sign-out.** No `qc.clear()` or
  `removeQueries` exists anywhere in `src/` (verified). `useSignOut` does a
  client-side `navigate('/sign-in')`, so with `staleTime: 30s` a passkey
  sign-in by a second user within 30s renders the first user's lists, gear,
  and items without a refetch. The magic-link path and account deletion both
  avoid this by using `window.location.assign` - sign-out is the one door
  left open. Server never serves cross-account data; this is purely a client
  cache leak, but it is visible on a shared device.
- **Mutation failures on `/gear` leave dialogs open with no feedback.** None
  of the six gear mutations sets `meta.errorToast`, and every one closes its
  dialog from a call-site `onSuccess` with no error path. `GearItemDialog`
  already has a `saveError` prop that `ListDetailPage` uses and
  `GearLibraryPage` does not. With the server down the dialog just sits there.
- **`DesktopListsPanel` is a 643-line fork of `ListsPage`** - same dialog
  state machine, same import wiring, same drag orchestration, same row
  chrome. The missing error handling above is absent from both because there
  is no shared component to fix once.
- **`sharedListAll` documents an invalidation nobody performs.** The key
  exists only at its own definition (verified). Either wire it into the list
  write paths or delete it and the comment that promises it.

### Tests

The suite is strong; these are the specific holes.

- **`makeOptimisticPackReorder` has zero tests** (verified: referenced only
  in `optimistic.ts` and `ListDetailPage.tsx:659`). Its sibling
  `makeOptimisticReorder` has 12. It shipped in the most recent PR, it is a
  ~90-line near-copy whose *divergent* behavior is what is untested, and its
  failure mode is silent: a validator bug makes every pack drag do nothing
  with no toast, because `onError` early-returns on that error class.
- **The 409 path is untested on both sides** - `grep 409` across all client
  tests returns nothing (verified). This is the only concurrent-reorder
  conflict path the app has.
- **The 200-food-item cap is never exercised at the boundary** (verified).
  Every other cap is - 100 lists, 300 items, 500 gear, 30 locations - each
  proving both the friendly 422 and the trigger backstop. Food is the newest
  trigger and therefore the likeliest to be off by one.
- **`isAnyUniqueViolation` and `isForeignKeyViolation` are untested**
  (verified), and `db-errors.ts:44-48` has a comment/code mismatch: it claims
  *"SQLITE_CONSTRAINT_UNIQUE pins the class"* while checking only the weaker
  `SQLITE_CONSTRAINT`. `isAnyUniqueViolation` is the sole discriminator for
  the pack-order 409.
- **Four of five food routes have no anon/401 test** (verified:
  `food.test.ts` contains exactly one 401 assertion, for `GET /food`). It is
  the only route file that does not use the table-driven anon loop the other
  four use, and `docs/authz-matrix.md` claims the coverage.
- **The authz matrix overstates three rows**: pack-order's tests are in
  `packing-locations.test.ts`, not `lists.test.ts`; its 409 claim has no
  test; the food rows' anon claims are the gap above.
- **`next*SortOrder` helpers are mocked at every call site and tested
  nowhere** - the mock *is* the assertion. The sparse-sequence behavior that
  is their entire reason for existing (deletes do not compact, so naive
  length-based picking collides) has no test.
- **Request-side URL/method drift is unpinned for `lists.ts`,
  `list-items.ts`, and `food.ts`** (24 functions). Rename a route on the
  server and the client 404s at runtime with nothing failing.

### Security

All four standing invariants **hold**, with code-level proof. No critical or
exploitable authorization defect was found. Three things are correct today
only because of something outside the code:

- **The auth-path gates match on `c.req.path`, which better-auth does not
  use** (it re-derives from `new URL().pathname`). These differ on dot
  segments. Not exploitable today - workerd normalizes them before the Worker
  sees the URL, which the reviewer confirmed by probing a live worker - but
  nothing in the repo holds it up, no test can express it (the harness
  normalizes too), and **the documented Node port makes it live**, silently,
  with all tests green. `requireFreshAuth` is also allow-by-default within
  its own mount, so a passkey-plugin minor that adds a credential-mutating
  endpoint ships it ungated. One change fixes both: invert to deny-by-default
  and canonicalize with `new URL(c.req.raw.url).pathname`.
- **A leaked share link cannot be revoked without destroying the list.**
  `generateSlug()` appears only in the four creation paths, never in `update`
  (verified). Unshare then re-share reactivates every link ever distributed.
  Rotate the slug on the false->true transition, or add a "reset share link"
  action.
- **The one anonymous endpoint is unmetered**, as is `/api/health`. Honestly
  recorded in SECURITY.md, and the in-file argument against a *DB-backed*
  counter is fair - but it concludes to "no control" rather than "a different
  control". `Cache-Control: public, max-age=60` on share responses would
  collapse repeat views at the edge with no counter at all.

Minor: CSRF's origin check is `if (origin && ...)` (verified), so an absent
`Origin` passes - not browser-exploitable, since the custom header is the
real gate, but weaker than SECURITY.md claims. CSP omits `object-src`.
`workers_dev` is not disabled, leaving a second unadvertised origin for the
share surface. `CLOUDFLARE_API_TOKEN` is job-scoped in `deploy.yml`, so it is
in env for `npm ci` and the vite build, not just the wrangler steps.

### Code quality

- **No server-side logging and no `app.onError`.** One `console.` in the
  whole server, in the dev-only email sender. Every repo correctly rethrows
  unknown errors - straight into Hono's default handler, which returns a bare
  `Internal Server Error`. The client half matches: `mutation-error-handler.ts`
  keys its log off `mutationKey`, and 1 of ~40 mutations sets one, so nearly

  make the careful error classification in `db-errors.ts` actually

- **`MAX_LIST_ITEM_QUANTITY = 9999` is declared twice** - `shared/lists.ts:19`
  and `src/lib/caps.ts:28`. The server validates one, every UI clamp reads the
  other. Five more caps are duplicated as literals, and cap numbers are
  hardcoded *inside* API error strings in 10 places, so changing `LIST_CAP`
  makes the API lie. `caps.ts:14-18` already re-exports three constants
  correctly - apply that to the rest.
- **Two dead feature flags still have live server write paths.**
  `readyChecksEnabled` is pinned `true` in the UI but still accepted on PATCH,
  written, and returned. `groupWorn` is worse: no component reads it, yet it
  is projected onto the **anonymous share wire**, and `shared/lists.ts:222`

- **`ListDetailPage.tsx` is 2217 lines**, ~1600 of it one component. The

  byte-identical in `csv/sort-keys.ts` and `queries/sort-keys.ts`, and the

- **Lint gaps**: `no-misused-promises` is off, so AGENTS.md's

## What is genuinely excellent

Worth naming, because it should survive future refactors.

- **The authorization boundary.** Every authenticated query filters on
  `userId`; every nested resource additionally filters on the *route's*
  parent id, so one of your own lists cannot reach another of your own lists'
  rows. That is the class of bug most apps ship. It is enforced by lint
  fail-closed, backed by composite same-owner FKs, and backed again by
  triggers. An IDOR would have to defeat three independent layers.
- **The share-leak test walks raw JSON**, not the parsed DTO - which is
  exactly the test that would otherwise be unable to see the leak it exists
  to catch. It checks snake_case spellings too, and populates `cost` and
  `purchaseDate` so "correctly omitted" is distinguishable from "nothing to
  omit".
- **`scripts/check-migration-safety.mjs`** encodes knowledge no tool
  documents: D1's inert `foreign_keys=OFF`, rebuild-drops-your-triggers,
  editing-an-applied-migration-is-a-no-op. It fails closed on unknown tables.
  Its own header: *"A human reviewer caught 0009. This script is that
  reviewer, made mandatory."*
- **Type safety.** Under `noUncheckedIndexedAccess`, the entire non-test tree
  has two non-null assertions, zero `any`, zero `@ts-expect-error`.
- **The rate limiter.** Three buckets with distinct threat models, charge
  ordering justified, the global charge deliberately moved inside
  `sendMagicLink` because the middleware sees an unvalidated body, HMAC'd
  bucket keys so `rate_limits` never becomes a plaintext address list. Every
  one pinned by a test, including a 12-way concurrent burst.
- **Account deletion is proven complete**, including the non-obvious half:
  `verification` has no `user_id`, so the cascade cannot reach it, and the
  `beforeDelete` hook purges pending magic links *by email* - otherwise a
  stale link would resurrect a deleted account. Tested, including that a
  bystander's identical artifacts survive.
- **The test suite is genuinely test-driven.** Across the last 80 commits,
  exactly two touched source without touching tests, both one-line fixes.
  Three commits are test-only. Retrofit commits are absent entirely. More
  telling than shape: the tests encode *failures*, citing the PR that found
  the bug and, in one case, noting that a prior assertion "documented the bug
  rather than a decision."
- **Commit hygiene and comment quality.** Comments explain why, not what -
  including, repeatedly, reasoning that turned out to be wrong, stated
  honestly.

## Recommended order of work

1. **C1 - the cascade/unique-index collision.** Design decision + a
   regression test with two Unassigned rows. Account deletion is currently
   breakable with no user workaround.
2. **C2 - gate `deploy.yml` on CI** via `workflow_run`. One YAML block, works
   on the free plan, and it converts the migration guard from habit to
   machine.
3. **The two `isError` gaps** (ListDetailPage, ListsPage) and **`qc.clear()`
   on sign-out**. Small, user-visible, and the first two are lying to users
   about data loss.
4. **`app.onError` + structured logging**, and `mutationKey`s on the
   mutations. Cheapest now, while the error-classification design is fresh.
5. **Wire `reorderPackItemsMut.isPending`**, and add tests for
   `makeOptimisticPackReorder` and the 409 path.
6. **Extend `check-migration-safety.mjs` to CHECK constraints and FKs.**
   Small, and it is the guard for the backstop the whole authz story leans on.
7. **Deduplicate the caps**, fix the cap-number-in-error-string sites, and
   retire `readyChecksEnabled` / `groupWorn` from the write paths (the latter
   also removes a dead field from the anonymous share wire).
8. **Doc sweep**: the stale paths and pins above, the `groupWorn` false
   rationale, and a decision on the ASCII rule. Consider generating STACK.md's
   version table from `package.json`, and a CI step that greps backticked
   paths in AGENTS.md and fails if they do not exist.

Items 1-3 are worth doing before the app has real users. The rest is ordinary
maintenance, and none of it is urgent.

## Structural risks, longer view

**The invariants live in comments rather than in types or tests, and three of
them are currently false.** This codebase reasons at an unusually high level -
the comments in `app-schema.ts`, `rate-limit.ts`, and `list-items.ts` are
better than most design docs. That is also the failure mode.
`chunkForParamCap` states an invariant drizzle does not honor;
`list-items.ts:349` states a 409 the route cannot produce; AGENTS.md states a
455-statement worst case the gear importer exceeds eightfold. C1 is the same
shape at the schema level: the pack-rank invariant is maintained meticulously

**Pack ordering is where complexity concentrates and where the next bug will
come from.** A per-cohort rank under two unique indexes, a two-phase
permutation write, a partial index for NULL cohorts, negative scratch values
that must never commit, and re-ranking obligations on every path that moves a
row between cohorts - that is a lot of invariant for one integer column, and
C1 shows it already has a hole. It needs a test helper that asserts cohort-rank
uniqueness after *every* mutating API call in the suite, rather than tests
that each happen to use one or two items.

**Doc drift will erode trust in the docs, and the docs are load-bearing
here.** This project runs on agents reading AGENTS.md and SECURITY.md as
authoritative. When AGENTS.md points at a deleted file, the next reader stops
trusting the parts that are right - including the D1 batch traps and the
FK-cascade warning, which are the most expensive knowledge in this repo.
